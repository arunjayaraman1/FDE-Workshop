01 · The problem

Shipping a new service costs 30–60 minutes of tribal knowledge — every time

An experienced engineer can scaffold a repo, wire CI, and add secrets in under an hour. But the result is different every time, nothing is reviewed, and nothing is recorded once it's done.

Operating idea

Sign in, pick a language and one of the 15 maintained templates (built-in, or scaffolded live from create-cloudflare), and configure name, org target, region, secrets, env vars, and bindings in one guided wizard. Launchpad scaffolds the project, creates the GitHub repo, sets provider credentials as encrypted repo secrets, and pushes — a GitHub Actions workflow then deploys, visible live on the page.

Deliberate scope boundary: Launchpad is not a PaaS or hosting platform. It owns the path from "ship this" to "live and wired to CI/CD" — and nothing after. Teams keep owning the runtime.
02 · The approach

Replace the platform ticket with a self-serve launcher

Launchpad doesn't add a new place to manage running apps — it removes the setup tax that sits in front of every one of them.

Before Launchpad

  • File a platform ticket and wait.
  • Hand-roll the repo, CI, and secrets from memory.
  • Every project ends up wired slightly differently.
  • No record of who has access or what changed.
  • Onboarding means learning tribal setup steps.

With Launchpad

  • Sign in and pick a maintained template.
  • Configure once in a guided wizard — name, org, region, secrets.
  • Launchpad scaffolds, creates the repo, sets secrets, pushes.
  • GitHub Actions deploys — visible live on the page.
  • Redeploys, env vars, bindings, invites, and an audit log, built in.
03 · Why it should exist

Speed and consistency, without giving up control

Speed over hand-rolled setup

Scaffolding a repo, wiring CI, and adding secrets costs 30–60 minutes per project today — Launchpad collapses that to roughly two minutes of guided clicks, identically every time.

Consistency beats tribal knowledge

Templates, workflows, and config live in one reviewed, versioned place. Update a template once and every future project inherits the fix.

Security by default

Least-privilege tokens, credentials encrypted at rest, provider keys stored as GitHub repo secrets, invite links with expiry, and a tamper-evident audit log.

One surface for Cloudflare and AWS

Workers/Pages and Lambda/Amplify side by side, so teams pick the runtime that fits the job — not the one someone remembers how to wire up.

04 · Feature highlights

One branded console, real team access, and a lock on the deployed app itself

Newpage Deploy Console

One branded home for every launch — signed into the "Newpage" workspace, with every project, template, and setting under a single console instead of a pile of separate tools.

Members & team access

Every project has owners and members. Owners send single-use invite links (7-day TTL) that grant Launchpad access and, with a GitHub handle, matching repo collaboration — admin for owners, push for members.

Site access keys

Turn on Site Access to gate the deployed app's live URL behind an access key — visitors hit a sign-in prompt before they ever reach the app, independent of who can sign into Launchpad itself.

05 · How it works

Sign-in to a deployed app, in five guided steps

Step 1Sign in

Shared org password plus a username. First user (or the configured admin) becomes global admin.

Step 2Pick a template

Language and one of 15 maintained templates across 5 categories — or a live create-cloudflare scaffold.

Step 3Configure

Name, visibility, GitHub org, region and credentials, env vars, bindings, preview and provisioning toggles.

Step 4Launch

Launchpad scaffolds the project, creates the repo, encrypts and sets secrets, and pushes to main.

Step 5Deploy

GitHub Actions deploys to Workers, Pages, Lambda (SAM), or Amplify — live on the launch page.

09 · Security & reliability

Secure by default, not by policy document

Least privilege

Tokens scoped to only what's needed — repo + workflow for GitHub, Edit permissions for Cloudflare, minimal IAM for AWS.

Credentials at rest

Per-project GitHub tokens and AWS keys are encrypted before being persisted; without a secret key, they simply aren't stored.

Deploy secrets

Provider credentials are set as GitHub-encrypted repo secrets and are never returned by any Launchpad API.

Session security

HMAC-signed session cookie, 8-hour TTL, HttpOnly, SameSite=Strict, with rate-limited logins.

Invite-based access

Single-use invite links expire after seven days; accepting one can also grant GitHub repo collaboration.

Full audit log

Every sign-in, launch, redeploy, delete, and env-var change is appended to a tamper-evident log.

10 · Scope

Deliberately narrow, on purpose

In scope

15 templates across 5 categories plus live scaffolders; a launch wizard with bindings, env vars, region/credentials, and preview/provisioning toggles; a projects table with search and bulk actions; a seven-tab project page; live logs and preview branches (Cloudflare); single-use invites; and settings with security status, org config, and a full audit log.

Out of scope

Launchpad is not a PaaS — it doesn't run the apps it deploys, and it can't be hosted on Cloudflare itself (it needs a filesystem and spawns create-cloudflare, so it runs on a Node host). Teams keep owning the runtime after launch.

11 · The twist
Two things exist today, not just a deck

This isn't a concept. We already built it — twice.

Alongside this proposal there are two real deliverables: a clickable interactive prototype that demonstrates every screen and flow, and the actual Launchpad application, which signs people in, creates real GitHub repos, sets real repo secrets, and triggers real GitHub Actions deploys to Cloudflare and AWS end to end today.

The interactive prototype

  • A single self-contained HTML file (prototypes/launchpad-full.html) that drives every screen and flow — login, launch wizard, animated deploy, live log stream, project tabs, invites, settings — with no backend.
  • Used for stakeholder demos and as the driving surface for the 7-minute walkthrough video script.
  • Matches the exact visual language of the real app, so a demo and the live product feel identical.

The real, working application

  • A Next.js app with real GitHub, Cloudflare, and AWS integrations — not a mock.
  • Real login and session security, encrypted credentials, and a real audit log.
  • A project launched through it is a real, deployed Worker, Pages site, Lambda, or Amplify app with CI/CD attached — today.

Ask for a live walk-through of either: the clickable prototype, or a real launch, end to end.
